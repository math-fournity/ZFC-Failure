**为什么必须走 checkpoint（一条值得记住的机制）**：`MEMORY/001` 属于 runtime 的 `MUTABLE` 集合
（经 `mutable_shard_paths`），而 `plan()` 在入口处逐条核 `HEAD.json.tracked` 的 sha256。
任何绕过事务直接改 `MEMORY/001` 都会让 `HEAD.json` 的哈希陈旧，随后 **runtime 拒绝加载一切**
（`UNCOMMITTED_STATE`）。本机因此出现过 20 分钟的 `BLOCKED`，正确解法不是手改 `HEAD.json`
（它是 machine-managed canonical asset，AGENTS.md 禁止绕过 manager 手改），而是把新内容作为
payload 的一部分交给 checkpoint 事务，由事务原子写入 `MEMORY/001` 与 `HEAD.json`。
prepare 脚本已落盘为 `scripts/audit/prepare_codex_cfc_plan_20261019_checkpoint.py`，可复用。

**两个可复用的机械坑**（下轮直接照做）：

原计划写的是"走 `capture_run.py` 生成新收据"。实测发现此路对 CG001 线**结构性关闭**，

  `PROOF_VERSION_CLOSURE.json`，`mark_proof_run_indexed.py` 的 `CLAIM_ID` 正则
  （`scripts/audit/proof_claim_ids.py`）也不认 `CG001-` 前缀。
- **没有**为此改造共享治理工具 `proof_claim_ids.py`：那需要单独授权，且与编号边界冲突。
- **没有**把本机实跑写成"新收据"或"MACHINE_PROVED 升级"：正式收据仍是 10-14 那份，
