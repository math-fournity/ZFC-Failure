## 1.2 证据链的真实形状：PDF 是凭据源、MD 已在库、PNG 只是审计辅助

初版底账在这里说"凭据源 PDF 不在库里、Z01/Q1 只存在于某台机器的工作树上"——
**这个说法夸大了**。核清后的真实链条是：

~~~text
zermelo1908-pp261-281.pdf ──MinerU──▶ zermelo1908-pp261-281.md ──▶ 证据文件的文字引文
        (未入库)                        (已在库)                    (已在库)
~~~

- `mineru_md/zermelo1908-pp261-281.md` **已入库**（`git ls-files` 确认），
  证据文件（`来源/05` L100、脚注缺口登记、完整性证书）引用的是这个 MD 的行号；
- 完整性证书登记的 PDF 摘要 `445cfb1993d7a2b6`，与工作树那个 PDF 的 sha256
  **逐字相符**——即工作树 PDF 就是证书认定的那一个，不是来历不明的新版本；
- 那 21 张 PNG 只是逐页视觉审计时的辅助材料，**证据文件的引文不依赖 PNG 的分辨率**。

所以 Z01/Q1 的凭据**并不缺**：文字引文 + 已入库 MD + 证书登记的 PDF 摘要三者齐备，
未入库的只是 PDF 二进制本体与辅助 PNG。

仍不代做的理由（比初版精确）：提交 26 MB PDF 二进制不改变任何证据内容（摘要已登记、
MD 已入库、引文已固定），它只是让"可独立重放"更完整。这属于该线的完整性选择，
不是本会话的缺口，也没有"两版并存"的风险——`git ls-files` 确认 PNG 只有一版在库。

## 1.1 那 21 个 `M` 究竟是什么（2026-10-21 复核，修正过一处误判）

初版底账把它们写成"新产物待入库"，**这是错的**。实测：

- 21 个 PNG **已经在 git 里**（`git ls-files` 确认），所以它们是"已入库证据被改写"，不是未入库新文件。
- 源 PDF `zermelo1908-pp261-281.pdf` 页面尺寸 **2000 x 3034 pts**（21 页，与 21 张图一一对应）。
- 按该尺寸反推：HEAD 版 `3334x5057` = **120 dpi**，工作树版 `4167x6321` = **150 dpi**
  （两者反推值分别是 120.02/120.01 与 150.00/150.00，即精确对应，不是巧合）。
- 体积随之变化（zermelo-01：4,904,199 → 6,479,938 B），colortype/bitdepth 不变（2 / 8）。
- **旁证**：同目录 `_visualcheck-audit/pages/zermelo1908-pp261-281/` 与 `_audit-binary/`、
  `_split/`、`_upload/` 的 mtime 同为 `2026-10-19 15:55`，与该 PDF 同批。
  另有一个反向检验：用该 PDF 以 250 dpi 重渲染得 `6944x10535`，**与工作树版不符**——
  所以工作树版不是 250 dpi（我一度这样误判，已在此更正），而是 150 dpi。

**判读**：这是罗素线在 2026-10-19 把 zermelo 视觉审计图从 **120 dpi 升到 150 dpi** 的
一次**未完成的批量升级**——PDF 与全部中间目录同一时刻生成，说明当时在重跑整条管线。
该线最后活动是提交 `675b0396f`（10-17），此后未再提交，升级中途停下。
zermelo 1908 是本 repo 迄今唯一全审的 PDF（21 页），是 Z01/Q1 引用句的凭据底座。

**为什么仍不提交**：新版至少与旧版一样有效（同页更高分辨率），但"用哪一版作凭据"
应由罗素线的 owner 决定。本会话代提交会造成两种后果之一——要么凭据底座被悄悄换成
本会话没审计过的一版，要么该线自己的提交历史被切开。两者都比留着不动更坏。
需要该线 owner 做的是：确认 250 dpi 版后**明确提交一次**，或在 `03-交接文档` 里
登记仍以 200 dpi 版为准并把工作树还原。

## 3. 为什么不去提交它们（不只是"不该"）

- **会污染他线 diff**：罗素考古线的会话仍在工作，提交它的中间产物
  会把它的工作单元切碎，导致它自己的 hook 与复查看到无法归属的提交。
- **共享树纪律**：2026-10-13 的 round31 删除事故后，仓库纪律是
  「共享树不删、核验用私有副本、重要 `.lean` 立刻入 git」。
  对并行会话的**未提交**文件，正确的动作是不动，而不是代它提交。
- **`_visualcheck/` 是过程产物**：视觉审计的逐页栅格化 PNG 是否入库，
  应由该线的 owner 决定（可能整目录进 `.gitignore` 更合适），不由本会话代决。
